## Gate 6a — Stripe MCP harness aggregate token reduction (hybrid)

**Target:** ≥ 80.7% (PRD §"Success Criteria — v1.1"; matches v1.0 anchor on
the same 28-tool surface to prevent regression).

**Status:** SKIPPED — re-run by board operator with `STRIPE_SECRET_KEY`
set before BOARD APPROVAL CHECKPOINT.

**Source:** `test/harness/report.json#hybrid.aggregate.overall_reduction_pct`
(written by `npm run harness`).

**Methodology:**
- `test/harness/stripe-harness.ts` extended additively with `measureHybrid(tools, vanillaChars)`.
- Spawns `npx -y @stripe/mcp` via `StdioClientTransport`; captures live `tools/list` (28 tools at v1.0 anchor).
- Builds `MCPackEngine(tools, { embeddings: { provider: createMiniLMProvider() } })`; waits for `hasVectors()=true`.
- Runs the same five v1.0 representative queries (`'create a payment'`, `'manage customers'`, `'subscription billing'`, `'issue refund'`, `'list invoices'`) through `engine.handleSearchTools`; sums returned-schema char counts vs vanilla payload chars; computes aggregate reduction pct.
- Adapter is dynamically imported inside `measureHybrid` so the v1.0 keyword
  block remains runnable when `STRIPE_SECRET_KEY` is unset (graceful skip
  matches the v1.0 harness pattern at lines 55-59).

**Re-run command (Plan 10-03):**
```bash

jq -r '.hybrid.aggregate.overall_reduction_pct' test/harness/report.json
```

**Pass criterion:** `>= 80.7`.

## Gate 6c — search_tools p99 latency delta vs keyword baseline

**Target:** hybrid p99 within 50 ms of v1.0 keyword baseline (PRD §"Success
Criteria — v1.1").

**Measured:** `3.057 ms` (hybrid p99 minus keyword p99, with local MiniLM,
50-tool synthetic corpus, 100 warm-cache search calls).

**Status:** PASS.

**Source:** `test/harness/perf-bench-report.json` — fields
`search_p99_keyword_ms`, `search_p99_hybrid_ms`, `search_p99_delta_ms`.

**Raw numbers (this run, 2026-04-27 17:10 UTC):**
- search_p99_keyword_ms: 0.238 ms
- search_p99_hybrid_ms:  3.296 ms
- search_p99_delta_ms:   3.057 ms (≤ 50 ms threshold)

**Methodology:** Synthetic 50-tool corpus (resource × action grid for
deterministic naming). Two engines: keyword-only and hybrid (real MiniLM
via `createMiniLMProvider()`). 10 warm-up calls per side discarded; 100
timed calls per side; p99 computed via sorted-array index. Same query
rotation across both engines for fairness.

## Gate 6d — Index build for 50-tool MiniLM

**Target:** ≤ 5,000 ms (PRD §"Success Criteria — v1.1").

**Measured:** `216.6 ms` (wall-clock from `new MCPackEngine(...)` to
`hasVectors() === true`).

**Status:** PASS.

**Source:** `test/harness/perf-bench-report.json#index_build_ms`.

**Notes:**
- First-ever invocation of `createMiniLMProvider()` downloads ~90 MB
  ONNX weights to `@huggingface/transformers/.cache/`. The local
  measurement here ran with the model already cached from a prior run;
  re-runs from a cold cache add ~30 s for the download (one-time cost,
  documented in CHANGELOG migration note).
- The 216.6 ms reflects 50 batched embeddings + Float32Array packing.
  An earlier cold-MiniLM run measured 4,093 ms — still well under the
  5,000 ms ceiling.
